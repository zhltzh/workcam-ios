Not fixed / recorded as risk notes (no code change):

- **RISK-W021-R1 (Low, informational)**: `PUT /photos/{photo_id}/original`
  reads the whole body into memory (`await request.body()`) with no
  direct request-size ceiling; an attacker who can register a photo
  (≤100 MiB declared) can still stream a large body that must hash to
  the registered sha256 to be persisted — the hash gate bounds what is
  stored, not what is buffered. The 100 MiB registration cap and the
  per-device rate limit bound abuse. A streaming/streamed-limit design
  is a protocol-level change and was NOT made unilaterally; flagged for
  the protocol owner.
- **RISK-W021-R2 (Low, inherited)**: the experimental upload surface's
  batch `507` / sweep / TTL behavior was reviewed as-is (loopback-gated,
  opt-in, production-vetoed) — unchanged, no action.

### B.1 `origin/dev/windows-b02-w014-offline-sync` (delivery `80b4bc1`)

Production surface touched: `app/api/sync.py` (+85), `app/db.py` (v9
migration, +34).

- Runtime: full suite on the branch → **644 passed, 3 skipped** (baseline
  632 + its 12 new tests) — not below baseline.
- Directed attacks (6/6 PASS, file
  `tests/test_w021_probe_w014.py` in the review worktree):
  - `local:` references only resolve inside the CALLER's own batch
    id_map; unknown/forward refs → typed `unresolved_local_ref` (409).
  - Replay of a batch containing local refs → duplicates, no new rows.
  - Same op id + changed payload → `op_id_conflict`.
  - Captured batch replayed with the attacker's token touches only
    attacker-owned resources; ledger is owner-scoped.
  - Resolved ids still pass executor ownership checks (B cannot
    annotate A's photo).
- Ledger hash is computed on the RAW payload (before local-ref
  resolution) — byte-identical replays hit the ledger; comment in code
  documents the property.
- v9 migration preserves `seq` values (cursor stability) — verified in
  their tests and confirmed in the migration SQL.
- **Verdict: PASS, no security findings.** Design note (non-security):
  an op rejected for a deterministic reason stays rejected in the
  ledger (inherited baseline semantics, documented); clients must use
  a fresh operation_id after fixing a rejected op.

### B.3 `origin/dev/windows-b02-w018-evidence-verifier` (delivery `88d9e15`)

Standalone offline CLI (`tools/evidence-verifier/verify_evidence.py`),
no production code touched. Reviewed the unpack surface on behalf of
B02-W018:

- zip-slip: absolute paths / drive letters / backslashes / `..`
  components / Windows case-insensitive destination collisions all
  rejected in a static pass BEFORE any extraction (CPython 3.12's
  read-side backslash normalization additionally resurfaces hostile
  names as `..` traversal, which the guard catches).
- Zip bombs: per-entry and total uncompressed-size guards (default
  1 GiB, `--max-uncompressed-mb`), extreme compression-ratio guard
  (>200x on entries >1 MiB).
- Exit-code contract: corrupt(2) > verify-failed(1) > ok(0), verified
  at runtime on a genuinely signed package (0), tampered photo (1),
  and corrupt inputs (2).
- Directed probes (8/8 PASS, script `probe_w018.py`): Windows reserved
  device names (`NUL`, `CON.txt`, `LPT1.txt`) → exit 2 fail-closed;
  `--max-uncompressed-mb 0` / negative → all entries rejected (guard
  fails CLOSED, not open); understated central-directory `file_size`
  (CRC/size lie) → exit 2; claimed-huge `file_size` → exit 2 with
  `exceeds size guard`; missing input → exit 2; valid dir package → 0;
  tampered photo → 1. Temp extraction dir is removed in a `finally`
  (unless `--keep-extracted`).
- Their tests: **42/42 pass** (includes zip-slip/bomb/orphan/exit-code
  precedence cases).
- **Verdict: PASS, no security findings.**
